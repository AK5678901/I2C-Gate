# 同じPico内の疑似I2Cデバイスでデバッグ

`i2c_gate.uf2` はフィルタと独立した疑似I2Cデバイスを同じRP2040に搭載します。ファームウェアは1種類で、疑似デバイスは常時動作します。外部ホストがフィルタ上流を操作し、下流信号をいったんGPIOに出してからジャンパ線で疑似デバイスへ戻します。ソフトウェア内でフィルタとスタブのデータを受け渡す経路はありません。

```text
外部I2Cホスト                  同じRaspberry Pi Pico
SDA ───── GP0 [フィルタ上流] → [フィルタ下流] GP2 ──ジャンパ── GP4 [疑似デバイス]
SCL ───── GP1                              GP3 ──ジャンパ── GP5 [I2C0 / 0x50]
GND ───── GND
```

## 配線

| 接続元 | 接続先 | Pico物理ピン |
| --- | --- | --- |
| 外部ホスト SDA | GP0（フィルタ上流 SDA） | 1 |
| 外部ホスト SCL | GP1（フィルタ上流 SCL） | 2 |
| 外部ホスト GND | Pico GND | 3など |
| GP2（フィルタ下流 SDA） | GP4（疑似デバイス SDA） | 4 → 6 |
| GP3（フィルタ下流 SCL） | GP5（疑似デバイス SCL） | 5 → 7 |

上流のSDA/SCLと下流のSDA/SCL、それぞれを3.3 Vへプルアップしてください。内部プルアップは無効です。上流と下流のSDA/SCLを直結しないでください。疑似デバイス側にも独立した別の電源は不要です。同一基板内のGNDを使用します。

信号レベルは3.3 Vです。まず100 kHz以下で確認し、ホスト側ではクロックストレッチを許可してください。フィルタは下流処理を待つ間、上流SCLをLowに保持します。下流の実効速度はGPIO処理と割り込みによって設定値より遅くなります。

## ビルドと起動

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build_pico.ps1
```

`build/pico/i2c_gate.uf2` をBOOTSELモードのPicoへコピーします。

疑似デバイスは起動直後から7 bitアドレス **0x50** で応答します。バス上のアドレスバイトはWRITEが `0xA0`、READが `0xA1` です。フィルタも起動直後から全対応アドレスをルールなしで中継するので、USB設定なしで `0x50` のスタブを利用できます。

フィルタ経由では、起動時の既定設定で試せます。設定済みルールを解除するには、GUIで `examples/stub-echo.json` を読み込んでUSB送信してください。全対応アドレス、下流100 kHz、ルールなしのパススルーになります。通常の `examples/filters.json` にはREAD先を `0x51` へ変更するルールがあり、そのままではこのスタブのREADは成功しません。スタブ自身のアドレスは `firmware/i2c_echo_stub.h` の `ECHO_STUB_ADDRESS` で固定しており、USB設定では変更されません。フィルタ設定を送信し直してもスタブのFIFOは消去しません。

スタブ単体を試す場合はGP2–GP4、GP3–GP5のジャンパを外し、外部ホストをGP4/GP5に直接接続してください。この場合、フィルタのUSB設定は不要です。フィルタ下流と外部ホストを同時に同じバスへ接続しないでください。

## スタブの仕様

- 下流WRITEのデータを4096バイトのFIFOへ追記します。レジスタアドレスの解釈はなく、最初のデータバイトもそのまま保存します。
- 下流READ要求ごとに先頭の1バイトを消費して返します。FIFOが空なら毎回 `0xFF` を返し、後からWRITEすれば再びそのデータを返します。
- STOP、Repeated START、READ終了時のNACKではFIFOを消去しません。複数WRITEの連結、分割READに対応します。リセットで空になります。
- TX FIFOへの先読み充填はせず、ハードウェアからの要求1回につき1バイトだけ供給します。正常なREADの最後のNACKで、次の未読バイトまで消費しないためです。READをバイト途中で異常中断した場合、すでに要求された1バイトは消費済みです。
- FIFOが満杯の場合は、新しく届いたバイトを捨て、既存の未読データを維持します。ハードウェアは受信をACKするため、オーバーフローをホストへNACK通知する機能はありません。
- デバッガで `echo_fifo.count`、`echo_fifo.underflows`、`echo_fifo.overflows` を確認できます。これらはスタブの割り込み内だけで更新します。
- フィルタの初期WRITE上限は1トランザクション256バイトです。FIFO容量とは別です。容量試験では短いWRITEを複数回行うか、GUI設定で上限を変更してください。

フィルタのWRITE変更は保存する値に、READ応答変更はホストへ返す値に反映されます。WRITEの遮断バイト以降はスタブへ届きませんが、先行バイトはすでに保存されています。READ応答の置換・遮断では、既存のフィルタ仕様どおり下流READとFIFO消費は発生します。

## 外部ホストで確認する手順

各行のREADは最終バイトをNACKで終了し、STOPを出してください。次の表は上から順に実行します。Picoを再起動し、フィルタ経由の場合は `examples/stub-echo.json` をUSB送信してから始めます。スタブ直結の場合は設定送信不要です。

| 操作（宛先はいずれも0x50） | 期待結果 |
| --- | --- |
| READ 2バイト | `FF FF`（初期状態のアンダーフロー） |
| WRITE `12 34 AB`、STOP、その後READ 5バイト | `12 34 AB FF FF` |
| WRITE `10 20 30`、STOP、その後READ 1バイト | `10` |
| 続けてREAD 3バイト | `20 30 FF`（短いREADで残りを捨てない） |
| WRITE `55 66`、Repeated START、READ 3バイト | `55 66 FF` |
| WRITE `00 FF`、STOP、WRITE `7E`、STOP、READ 4バイト | `00 FF 7E FF` |

WRITEは各バイトの受信直後に下流へ転送され、下流のACK/NACKが上流へ中継されます。遮断バイトにはNACKを返し、そのバイトを下流へ送りません。配線確認にはFIFOが空の状態から `0xFF` 以外を書き込み、読み返してください。`0xFF` だけのREADは、配線不良や下流エラー時のフィルタ代替値と区別できません。

ロジックアナライザでGP0/GP1とGP2/GP3を同時に観測すれば、フィルタの前後を比較できます。GP4/GP5はジャンパ接続によりGP2/GP3と同じ下流バスです。

## 実装と検証範囲

Core 1は既存の上流GPIO監視、Core 0は既存の下流GPIO制御とUSB処理を担当します。スタブは専用のハードウェアI2C0、GP4/GP5、FIFOを持ち、Core 0の割り込みで動作します。フィルタのサービス関数・設定・メールボックスには依存しません。Core 0が下流のクロックストレッチを待っている間も割り込みで応答できます。ただし同じMCUのCPU時間とリセットは共有します。[Pico SDKのI2CスレーブAPI](https://www.raspberrypi.com/documentation/pico-sdk/high_level.html#group_pico_i2c_slave)

単一ファームウェアのARMビルドとUF2生成を確認しました。CのFIFO実装について、アンダーフロー、追記と分割READ、満杯時の破棄、リングの折り返し、リセットをホスト側テストで検証しています。既存テストを含め36件成功しています。

実機配線による転送、I2C割り込みのタイミング、READ終了時のNACK、Repeated START、400 kHz動作は未検証です。上の手順で確認してください。
